# 1- Merge and rebase

## دﺳﺘﻮرﻫﺎی git merge و git rebase ﭼﻪ ﮐﺎری اﻧﺠﺎم ﻣﯽ دﻫﻨﺪ؟ ﺗﻔﺎوت آن ﻫﺎ را از ﻧﻈﺮ ﻧﺤﻮۀ ﺗﺮﮐﯿﺐ ﺗﻐﯿﯿﺮات و ﺷﮑﻞ ﺗﺎرﯾﺨﭽﮥ ﮐﺎﻣﯿﺖ ﻫﺎ ﺗﻮﺿﯿﺢ دﻫﯿﺪ. ﺑﺮای ﻫﺮ ﮐﺪام ﯾﮏ ﻣﻮﻗﻌﯿﺖ ﻣﻨﺎﺳﺐ اﺳﺘﻔﺎده ﺑﯿﺎن ﮐﻨﯿﺪ و ﺗﻮﺿﯿﺢ دﻫﯿﺪ ﭼﺮا در آن ﻣﻮﻗﻌﯿﺖ آن روش را اﻧﺘﺨﺎب ﻣﯽ ﮐﻨﯿﺪ.

در گیت، دو روش اصلی برای ادغام تغییرات از یک شاخه به شاخه دیگر وجود دارد: دستور `merge` و دستور `rebase`
## دستور git merge:

برای ادغام دو شاخه در یکدیگر استفاده میشود و تاریخچه ی واقعی هردو شاخه را حفظ میکند.
## نحوه ی ترکیب تغییرات:

اگر مثلا از شاخه ی master یک شاخه ی جدید به اسم topic زده باشیم و در master کامیت های F و G را انجام بدهیم و در topic هم کامیت های  A و B و C، 

دستور `git merge topic` تغییراتی را که روی شاخه‌ی `topic` از زمانی که از `master` جدا شده (یعنی کامیت `E`) تا کامیت فعلی‌اش (`C`) اعمال شده‌اند، روی `master` بازپخش می‌کند و نتیجه را در یک کامیت جدید ثبت می‌کند. همراه با نام دو کامیت والد و یک پیام لاگ از طرف کاربر که تغییرات را توضیح می‌دهد. پیش از اجرای این عملیات، Head روی نوک شاخه‌ی فعلی (`G`) تنظیم می‌شود.
نکته درمورد این کامیت جدید این است که دو والد دارد و اینکه اگر شاخه ی master بعد از اینکه topic از آن جدا شد، کامیت جدیدی نمیداشت، دیگر این کامیت سوم یعنی H اجرا نمیشد و master درواقع fast forward میشد یعنی اشاره گر آن میپرید روی C.



           A---B---C topic
         /         \
    D---E---F---G---H master
    

## یک موقعیت مناسب:

مثلا یک وبسایت داریم و در جایی تصمیم میگیریم که یک فیچر جدید به آن اضافه کنیم اما نمیخواهیم همینطوری روی شاخه ی اصلی برنامه و تست نشده اینکار را انجام بدهیم. پس ابتدا یک شاخه ی جدید میسازیم، فیچر جدید را طراحی کرده و در نهایت به شاخه ی اصلی میرویم و با آن merge میکنیم.


## دستور git rebase:

با این دستور میتوانیم تمام تغییراتی را که در یک شاخه ثبت شده اند بگیریم و در شاخه ی دیگر اجرا کنیم.


## نحوه ی ترکیب تغییرات:

           A---B---C topic
         /         
    D---E---F---G master
    
مثلا الان در همین مثالی که برای merge داشتیم، اگر دستور git rebase master را وقتی که در شاخه ی topic هستیم اجرا کنیم، این عملیات با رفتن به والد مشترک دو شاخه (شاخه فعلی و شاخه‌ای که می‌خواهید بازپایه‌گذاری کنید)، گرفتن تفاوت‌هایی که هر کامیت روی شاخه فعلی ایجاد کرده، ذخیره این تفاوت‌ها در فایل‌های موقتی، ریست کردن شاخه فعلی به همان کامیتی که شاخه مقصد دارد، و در نهایت اعمال هر تغییر به ترتیب انجام می‌شود.
و در نهایت به همچین چیزی میرسیم:
           ~~A---B---C~~ 
         /         
    D---E---F---G master --C' topic

حالا اگر به شاخه ی master بریم و git merge topic بزنیم، fast forward اتفاق افتاده و head هر دو شاخه روی C' قرار میگیرد.

    D---E---F---G --C' topic & master
    
در نهایت مخزن ما با حالت merge تفاوت محتوایی نخواهد داشت، ولی در تاریخچه ی کامیت ها می بینیم که در حالت rebase منظم تر و خطی است.
## یک موقعیت مناسب:

به همان علت تاریخچه ی منظم و خطی بودن، دستور git rebase بدرد وقتی میخورد که مثلا شما روی یک ریپازیتوری که برای خودتان نیست کار میکنید و میخواهید تغییراتی را اعمال کنید. بعد از اینکه در شاخه ی خودتان اینکار را انجام دادید آن را در شاخه ی اصلی rebase میکنید و حالا صاحب ریپازیتوری تنها کافیست یک git merge ساده انجام بدهد و فرایند شفاف تر و راحت تر خواهد بود.

 # 2- انتخاب بخشی از تغییرات
  ## ﻣﻨﻈﻮر از ﺑﺨﺶ ﺗﻐﯿﯿﺮات (hunk) در ﺧﺮوﺟﯽ ﻣﻘﺎﯾﺴﮥ ﺗﻐﯿﯿﺮات (diff) در Git ﭼﯿﺴﺖ؟ ﺗﻮﺿﯿﺢ دﻫﯿﺪ ﭼﮕﻮﻧﻪ ﻣﯽ ﺗﻮان ﺑﺎ اﺳﺘﻔﺎده از ﺧﻂ ﻓﺮﻣﺎن، ﺗﻐﯿﯿﺮات ﯾﮏ ﻓﺎﯾﻞ را ﺑﻪ ﺻﻮرت ﺗﻌﺎﻣﻠﯽ ﺑﺮرﺳﯽ ﮐﺮد و ﻓﻘﻂ ﺑﻌﻀﯽ از ﺑﺨﺶ ﻫﺎ را ﺑﺮای ﮐﺎﻣﯿﺖ ﺑﻌﺪی در ﻧﺎﺣﯿﮥ staging ﻗﺮار داد. دﺳﺘﻮرﻫﺎ و اﻧﺘﺨﺎب ﻫﺎی ﻻزم را ذﮐﺮ ﮐﻨﯿﺪ و ﺑﮕﻮﯾﯿﺪ اﯾﻦ ﮐﺎر ﭼﻪ ﻓﺎﯾﺪه ای ﺑﺮای ﺳﺎﺧﺘﻦ ﮐﺎﻣﯿﺖ ﻫﺎی ﻣﻨﺴﺠﻢ دارد.


در خروجی دستور `diff`، یک Hunk بخشی از فایل است که تغییرات مربوط به یک ناحیه را نشان می‌دهد. هر Hunk معمولاً شامل خطوط حذف‌شده، اضافه‌شده و تعدادی خط از اطراف آن‌هاست تا محل تغییر مشخص باشد.

- خطوطی که با `-` شروع می‌شوند، حذف شده‌اند.
- خطوطی که با `+` شروع می‌شوند، اضافه شده‌اند. 
- خطوط بدون علامت، برای نمایش زمینه و درک تغییرات هستند.

## چگونه فقط بخشی از تغییرات را برای کامیت انتخاب میکنیم؟

با نوشتن این دستور :
```bash
git add -p <filename>
```

این دستور تغییرات فایل را به صورت تعاملی نمایش میدهد و برای هر hunk گزینه هایی را ارائه میکند:


|گزینه|عملکرد|
|---|---|
|`y`| Staging به hunk افزودن|
|`n`|hunk رد کردن|
|`s`|  به بخش های کوچکترhunk تقسیم|
|`e`|hunk ویرایش دستی|
|`q`|خروج از حالت تعاملی|




برای مثال، اگر در یک فایل هم اصلاح یک باگ و هم تغییر ظاهر برنامه را انجام داده باشیم، می‌توانیم فقط Hunk مربوط به اصلاح باگ را با گزینه `y` به Staging اضافه کنیم و تغییرات ظاهری را فعلاً کنار بگذاریم.
بعد با این دستور وضعیت را بررسی کرده و تغییرات انتخاب شده را commit میکنیم:
```bash
git diff --staged
git commit -m "Fix the login bug"
```

## این کار چه فایده ای دارد؟
- باعث میشود هر commit  هدف مشخصی داشته باشد
- بررسی و درک ساختار پروژه آسانتر شود
- بازبینی کد و پیدا کردن علت خطاها راحتتر شود
- تغییرات نامرتبط در یک commit ترکیب نمیشوند. (نوشتن پیام کامیت راحتتر میشود)

# 3 - یافتن منشا خطا
## دﺳﺘﻮر git bisect ﭼﮕﻮﻧﻪ ﮐﺎر ﻣﯽ ﮐﻨﺪ؟ ﻣﺮاﺣﻞ ﭘﯿﺪا ﮐﺮدن ﮐﺎﻣﯿﺘﯽ را ﮐﻪ ﯾﮏ ﺧﻄﺎ را وارد ﮐﺮده اﺳﺖ،از ﻣﺸﺨﺺ ﮐﺮدن ﯾﮏ ﮐﺎﻣﯿﺖ ﺳﺎﻟﻢ و ﯾﮏ ﮐﺎﻣﯿﺖ ﻣﻌﯿﻮب ﺗﺎ ﭘﺎﯾﺎن ﺟﺴﺖ وﺟﻮ، ﺗﻮﺿﯿﺢ دﻫﯿﺪ. ﯾﮏ ﻣﺜﺎل از ﮐﺎرﺑﺮد آن ﺑﯿﺎورﯾﺪ و ﺗﻮﺿﯿﺢ دﻫﯿﺪ ﭼﺮا اﯾﻦ روش ﺑﺮای ﯾﺎﻓﺘﻦ ﻣﻨﺸﺄ ﺧﻄﺎ ﻣﻔﯿﺪ اﺳﺖ

این دستور برای پیدا کردن این کامیت از binary search استفاده میکند.
شیوه ی کارش به این صورت هست که ابتدا دستور زیر را وارد کرده،
```bash
$ git bisect start
```
و بعد دو نقطه ی bad و good را در تاریخچه ی کامیت ها به عنوان نقاط بازه ی مان مشخص میکنیم. مثلا به این صورت:
```bash
$ git bisect bad (current version is bad)
$ git bisect good v2.7.1
```
حالا وقتی این دو کامیت خوب و بد را مشخص کرده باشیم، git bisect یک کامیت در میان این ها انتخاب میکند و به ما نشان میدهد. و مثلا این خروجی را نشان میدهد:
Bisecting: 600 revisions left to test after this (roughly 10 steps)
حالا ما باید آن نسخه را تست کنیم و good/bad بودن آن را مشخص کنیم. مثلا اگر این کامیت مشکلی را وارد نکرده باشد:
```bash
git bisect good
```
و بعد همچین خروجی ای را مشاهده خواهیم نمود:
Bisecting: 337 revisions left to test after this (roughly 9 steps)
فرایند را تکرار میکنیم تا وقتی که دیگر revisionای برای اصلاح باقی نمانده باشد و reference ما در این لحظه به اولین کامیتی که باگ وارد کرده اشاره خواهد نمود.
و حالا کارهای دیگری را هم با این git bisect میتوان انجام داد مثلا اگر دنبال نسخه ای باشیم که تغییر خاصی را وارد نموده باز هم این دستور میتواند به کار بیاید و فقط برای پیدا کردن کامیت باگ دار نیست.

## چرا این روش برای یافتن منشا خطا مفید است؟

- ساده و قابل مشاهده است
- سریع است! به جای گشتن در N کامیت از جستجوی باینری استفاده میکند
- خودکار کار میکند و ما فقط کامیت ها را نگاه میکنیم و میگوییم خوب بوده یا بد
- قابل خودکار سازی هم هست مثلا اگر یک scriptای داشته باشیم که به ما بگوید یک کامیت خوب بوده یا نه میتوانیم اجرا کنیم: 
```bash
git bisect run <script>
```

4 - بررسی تغییرات پیش از کامیت
ﻓﺮض ﮐﻨﯿﺪ ﻓﺎﯾﻞ README.md در ﻣﺨﺰن tracked اﺳﺖ و ﻗﺒﻼ ً ﮐﺎﻣﯿﺖ ﺷﺪه اﺳﺖ. ﺑﺨﺸﯽ از ﺗﻐﯿﯿﺮات ﺟﺪﯾﺪ آن را وارد ﻧﺎﺣﯿﮥ staging ﮐﺮده اﯾﺪ و ﺳﭙﺲ، ﺑﺪون اﺟﺮای دوﺑﺎرۀ دﺳﺘﻮر اﻓﺰودن ﺑﻪ اﯾﻦ ﻧﺎﺣﯿﻪ، ﻫﻤﺎن ﻓﺎﯾﻞ را ﻣﺠﺪدا ً وﯾﺮاﯾﺶ ﮐﺮده اﯾﺪ. ﻫﻤﭽﻨﯿﻦ ﭘﻮﺷﻪ ای ﺑﻪ ﻧﺎم /tmp دارﯾﺪ ﮐﻪ ﻓﻘﻂ ﺷﺎﻣﻞ ﻓﺎﯾﻞ ﻫﺎی ﻣﻮﻗﺖ و untracked اﺳﺖ. 
## 1- ﺑﺎ ﭼﻪ دﺳﺘﻮرﻫﺎﯾﯽ وﺿﻌﯿﺖ ﻣﺨﺰن، ﺗﻐﯿﯿﺮات ﻫﻨﻮز واردﻧﺸﺪه ﺑﻪ ﻧﺎﺣﯿﮥ staging و ﺗﻐﯿﯿﺮات آﻣﺎدۀ ﮐﺎﻣﯿﺖ را ﺑﺮرﺳﯽ ﻣﯽ ﮐﻨﯿﺪ؟ ﺗﻔﺎوت دو دﺳﺘﮥ ﺗﻐﯿﯿﺮات اﺧﯿﺮ را ﺗﻮﺿﯿﺢ دﻫﯿﺪ.

برای بررسی وضعیت کلی مخزن از دستور زیر استفاده میکنیم:
```
git status
```
ین دستور وضعیت فایل‌ها را نشان می‌دهد. برای مثال، مشخص می‌کند کدام تغییرات وارد ناحیه‌ی `staging` شده‌اند، کدام تغییرات هنوز در این ناحیه قرار نگرفته‌اند و کدام فایل‌ها `untracked` هستند.
برای مشاهده ی تغییرات وارد نشده به staging از:
```
git diff
```
استفاده میکنیم. این دستور تغییرات موجود در فایل های tracked را که هنوز به ناحیه ی staging اضافه نشده اند، نسبت به نسخه ی staging نمایش می دهد.

برای دسته ی دوم، یعنی تغییرات آماده ی commit، از:
```
git diff --staged
```
استفاده میکنیم. این دستور تغییرات ناحیه ی staging را نسبت به آخرین commit نمایش میدهد

در این سؤال، چون ابتدا بخشی از تغییرات `README.md` را وارد staging کرده‌ایم و سپس فایل را دوباره ویرایش کرده‌ایم، فایل ممکن است هم‌زمان دو دسته تغییر داشته باشد: تغییرات آماده‌ی commit و تغییرات جدیدی که هنوز وارد staging نشده‌اند.

## 2- اﮔﺮ در ﻫﻤﯿﻦ وﺿﻌﯿﺖ ﯾﮏ ﮐﺎﻣﯿﺖ ﻣﻌﻤﻮﻟﯽ و ﺑﺪون ﮔﺰﯾﻨﮥ a-ﺛﺒﺖ ﮐﻨﯿﺪ، ﮐﺪام ﺗﻐﯿﯿﺮات ﻓﺎﯾﻞ در آن ﻗﺮار ﻣﯽ ﮔﯿﺮﻧﺪ و ﮐﺪام ﺗﻐﯿﯿﺮات ﺑﺎﻗﯽ ﻣﯽ ﻣﺎﻧﻨﺪ؟ دﻟﯿﻞ ﭘﺎﺳﺦ ﺧﻮد را ﺑﯿﺎن کنید. 

اگر یک کامیت معمولی انجام دهیم، فقط تغییراتی در آن قرار میگیرند که در staging هستند (یعنی قبل از ویرایش مجدد فایل)
تغییرات جدیدی که پس از اجرای `git add` ایجاد شده‌اند، در Working Directory باقی می‌مانند و در این commit ثبت نمی‌شوند؛ زیرا Git هنگام commit معمولی، محتوای staging را ثبت می‌کند، نه تمام تغییرات فایل‌های کاری. اگر بخواهیم آن ها هم اضافه شوند باید مجدد git add README.md را اجرا کنیم 

## 3- ﺑﺮای ﺟﻠﻮﮔﯿﺮی از اﺿﺎﻓﻪ ﺷﺪن ﻓﺎﯾﻞ ﻫﺎی ﭘﻮﺷﮥ /tmp ﺑﻪ ﮐﺎﻣﯿﺖ ﻫﺎی ﺑﻌﺪی، ﭼﻪ ﺗﻨﻈﯿﻤﯽ و در ﮐﺪام ﻓﺎﯾﻞ اﻧﺠﺎم ﻣﯽ دﻫﯿﺪ؟ آﯾﺎ ﻫﻤﯿﻦ ﺗﻨﻈﯿﻢ ﺑﺮای ﻓﺎﯾﻠﯽ ﮐﻪ ﻗﺒﻼ ً tracked ﺷﺪه اﺳﺖ ﻧﯿﺰ ﮐﺎﻓﯽ اﺳﺖ؟ ﺗﻮﺿﯿﺢ دﻫﯿﺪ
در این قسمت باید به سراغ .gitignore برویم. در این فایل این الگو را قرار میدهیم:
/tmp/
یعنی به آن میگوییم که فایل های داخل این پوشه را نادیده بگیرد.
و خیر برای فایلهای tracked کافی نمیباشد و فقط برای untrackedهایی که با الگوی آن مطابقت دارند عمل میکند. 
اگر فایلی قبلاً tracked شده باشد و بخواهیم Git دیگر تغییرات آن را پیگیری نکند، باید آن را از index خارج کنیم، بدون اینکه فایل محلی حذف شود:
```
git rm --cached path/to/file
```
برای خارج کردن تمام فایل‌های tracked داخل پوشه‌ی `tmp`، در صورت نیاز می‌توان از دستور زیر استفاده کرد:
```
git rm -r --cached tmp/
```
پس از آن، با ثبت تغییرات مربوط به index و وجود الگوی مناسب در `.gitignore`، فایل‌های این پوشه دیگر در commitهای بعدی پیگیری نمی‌شوند؛ البته تا زمانی که دوباره به‌صورت صریح به Git اضافه نشوند.
